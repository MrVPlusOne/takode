# Memory -- Leader Brief

Use this mandatory final phase after the quest's substantive result has been accepted and synced when applicable. From the user's perspective, Memory is asynchronous post-processing: the leader reports the accepted Work outcome as Memory begins rather than waiting for closure. The quest remains technically open in `MEMORY` until Memory finishes.

Memory is strict non-project-tracked durable-state closure. It owns final `User review checks` settlement, final debrief metadata, quest metadata reconciliation, quest-note hygiene, memory consistency checks, memory writes or explicit deferrals, stale-memory checks, cleanup, external durable-state records, and follow-up routing.

Boundary:
- Keep the board row in `MEMORY`. A v2 row reaches this state only through the guarded Work -> Memory transition, which requires fresh synchronized target code SHAs or explicit zero-code request evidence.
- For tracked Work, verify the synchronized selected-target SHAs are already present as structured quest code commit metadata. If they are absent, wrong, or only present in prose, return the assigned worker to Work; do not ask Memory or the leader to first-attach them during completion. Memory may attach only separate file-based memory-repository commits.
- If the accepted Work outcome was not already reported at the transition, report it now from the current Work note before waiting on Memory. Do not present this outcome update as final quest completion; final Memory remains mandatory.
- Include the exact assignee brief path in the instruction: `~/.companion/quest-journey-phases/memory/assignee.md`.
- Assign ownership explicitly only when deviating from the normal same-worker Memory owner. Use an independent reviewer for policy, provenance, or memory-consistency risk; use a leader or curator for dependency, timer, notification, no-worker, dashboard/state, external-state, artifact-heavy, or cross-quest durable-state closure.
- Do not ask Memory to edit tracked project files. If tracked docs, skills, prompts, phase briefs, code, tests, templates, fixtures, changelog, notebooks, or other project repo files need changes, route the assigned Work worker back to Work. Use a separate quest only when the authoritative lifecycle rule in `takode-orchestration/quest-journey.md` permits it.
- When accepted scope still includes implementation or another evidence-bearing delivery, apply the lifecycle guide's delivery-evidence guard before accepting Memory entry. A selected design without the required delivery evidence is unfinished Work; design-only or investigation results use their own accepted completion evidence and the transition's explicit zero-code mode when they produced no tracked changes.
- Ask Memory to check whether the quest title, TLDR, and description still match the accepted delivered scope. Clear final-scope drift can be refreshed during Memory; ambiguous, contentious, or intent-changing edits should route back to the leader or user instead of silently changing scope. Do not use this as a way to rewrite active scope or unfinished quests.
- If a dependent quest is waiting on this quest, it may start once the parent reaches Memory because the substantive result is accepted and synced when applicable. Do not start a dependent that explicitly requires an output produced by Memory; keep that exceptional dependency waiting by leader judgment. Keep the parent row open until Memory finishes.
- Answer ordinary read-only follow-up questions during Memory from the accepted Work/Memory evidence or the context-rich responsible worker without reopening the quest. Rework is required only when the user changes the accepted result or requests new investigation, implementation, validation, or another substantive deliverable.
- Final `User review checks` are user-owned checks only. Memory should complete with an empty list when no user action remains, or with concise items only when the user still needs to inspect or do something after all agent-owned evidence is complete. Tests, Work verification, sync/push status, Memory closure, and other agent-owned evidence belong in phase docs, artifacts, commit metadata, and the debrief, not in final checks.
- Provide only deltas the assignee is unlikely to infer from the phase brief, quest record, current artifacts, or their own context: accepted refs, unusual durable-state risk, exact memory files or terms already inspected, external artifact locations, dependency/thread/notification cleanup needs, or known stale-memory concerns.
- Require phase documentation before completion. It should use phase-scoped quest feedback with full agent-oriented detail plus TLDR metadata when working on a quest, falling back to explicit `--phase memory` if current-phase inference is unavailable.
- Preserve any legacy `outcome` field as opaque read-only recovery data. It is not final-debrief authority and must not be promoted, rewritten, or deleted during Memory; complete normal debrief metadata from accepted quest evidence.
- Complete the quest only after Work-owned code evidence is already settled, final `User review checks`, quest metadata reconciliation, final debrief metadata, debrief TLDR metadata, exactly one memory statement, and any separate memory-repository commit metadata are settled.

Do not ask the Memory assignee to repeat the Work report. The leader has already surfaced that user-facing outcome; Memory closes durable state, verifies that the right record owns the durable facts, completes the quest when ready, and routes any remaining gaps.
